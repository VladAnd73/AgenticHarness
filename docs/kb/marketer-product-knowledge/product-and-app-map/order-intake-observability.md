## What it is
An **internal back-office area for Marketer staff** (CSMs / support / ops) that makes the **campaign-order round-trip with an external CRM** auditable. Two panels are deliberately **mirror lenses on the same round-trip** ([HK-502](https://linear.app/newbuilds/issue/HK-502) · PR [#14216](https://github.com/marketertechnologies/marketer/pull/14216)):
- **Orders Overview** = *receipt-first*, the **inbound** leg — "Vitec / Webtop / the M360 portal sent us an order — where did it come from, and was it accepted?"
- **Auto Order Attempts** = *attempt-first*, the **outbound** leg — "**we** tried to trigger an order by tagging a property's checklist in Vitec — what happened, and did Vitec ever call back?"

The stated problem it solves: the inbound leg previously left a trace only in Sentry, and the outbound auto-order pipeline **left no trace at all** when it skipped or failed — "a pipeline that dies at stage 0 (property ineligible) or stage 1 (checklist push returns 5xx) is invisible to ops today" ([HK-501](https://linear.app/newbuilds/issue/HK-501) · PR [#14215](https://github.com/marketertechnologies/marketer/pull/14215)).

Like the Failed Campaigns dashboard, these are **Rails (M2 `marketer` repo) Administrate-hosted pages — NOT the M360 React SPA.** They are custom `index` / `show` actions with service-object queries and Pagy pagination, not full Administrate resources ([HK-476](https://linear.app/newbuilds/issue/HK-476) · PR [#14200](https://github.com/marketertechnologies/marketer/pull/14200)).

**Routes** (M2 `config/routes/admin_panel.rb` @ `v1.376.0`):
- `/admin_panel/orders_overview` (index) and `/admin_panel/orders_overview/:uuid` (drill-down) — [HK-476](https://linear.app/newbuilds/issue/HK-476) · PR [#14200](https://github.com/marketertechnologies/marketer/pull/14200), [HK-477](https://linear.app/newbuilds/issue/HK-477) · PR [#14203](https://github.com/marketertechnologies/marketer/pull/14203)
- `/admin_panel/auto_order_attempts` (index), `/admin_panel/auto_order_attempts/details` (per-group drill-down) and `/admin_panel/auto_order_attempts/:uuid` (per-attempt show) — [HK-501](https://linear.app/newbuilds/issue/HK-501) · PR [#14215](https://github.com/marketertechnologies/marketer/pull/14215), [HK-502](https://linear.app/newbuilds/issue/HK-502) · PR [#14216](https://github.com/marketertechnologies/marketer/pull/14216)
- `/admin_panel/checklist_pushes/:uuid` (show only — no index) — [HK-504](https://linear.app/newbuilds/issue/HK-504) · PR [#14218](https://github.com/marketertechnologies/marketer/pull/14218)

**Sidebar:** *Orders Overview* and *Auto Order Attempts* are hand-written nav links beside *Failed Campaigns* and *Maintenance Mode*; *Checklist Pushes* deliberately never appears, because it has no index ([HK-501](https://linear.app/newbuilds/issue/HK-501) · PR [#14215](https://github.com/marketertechnologies/marketer/pull/14215); [HK-504](https://linear.app/newbuilds/issue/HK-504) · PR [#14218](https://github.com/marketertechnologies/marketer/pull/14218)).

## Who uses it
**Marketer staff — CSMs, support, ops. Not customer users.** Same audience as the Admin Panel generally (see the *Admin Panel* row in [Product & App Map](../product-and-app-map.md)).

Access is the standard admin gate: every controller inherits `AdminPanel::ApplicationController`, whose `authenticate_admin!` before-action admits only an `Admin` record — and the `Admin` model carries `default_scope { where(super_admin: true) }`, so *admin* and *super-admin* are the same population here ([HK-476](https://linear.app/newbuilds/issue/HK-476) · PR [#14200](https://github.com/marketertechnologies/marketer/pull/14200); confirmed in M2 `app/models/admin.rb:5` @ `v1.376.0`). No new role, seat or permission was introduced — nothing to add to *Personas, Roles & Account Structure*.

## ⚠️ The screens are live; the data is not
**At tag `v1.376.0` the three tables behind these panels have no production writers, so in production every list, drill-down and chart renders empty.** This is **staged delivery exactly as the tickets specify**, not a defect: the schema ticket states outright *"No writes wired up yet — that is Ticket 2 (intake writes) and Ticket 3 (auto-order writes). This ticket only lands the schema + models + factories + model specs so the follow-ups have something to write to"*, and makes it a Definition-of-Done item that a search for the three model names in `app/` returns only the model files ([HK-473](https://linear.app/newbuilds/issue/HK-473) · PR [#14188](https://github.com/marketertechnologies/marketer/pull/14188)).

Those two writer tickets — [HK-474](https://linear.app/newbuilds/issue/HK-474) (*Write `campaign_order_intake_receipts` at Vitec + Webtop webhooks and M360 portal mutation*) and [HK-475](https://linear.app/newbuilds/issue/HK-475) (*Write `vitec_auto_order_attempts` across stages 0–4 + `vitec_checklist_pushes` from `MarkChecklistJob`*) — are both **still *In Review*** in Linear as of 2026-08-26 and are not in this release. Re-verified in code at the tag: a repository-wide grep for **`CampaignOrderIntakeReceipt`**, **`Vitec::AutoOrderAttempt`** and **`Vitec::ChecklistPush`** under **`app/`** and **`config/`** returns only the three model files (**`campaign_order_intake_receipt.rb`**, **`vitec/auto_order_attempt.rb`**, **`vitec/checklist_push.rb`** under **`app/models/`** @ **`v1.376.0`** — the same three the *Sources* table lists; matched on the unqualified class names, since the two **`Vitec::`** models declare **`module Vitec`** / **`class AutoOrderAttempt`** and **`class ChecklistPush`** and so never contain their own fully-qualified constant) plus the read-side admin controllers, services, helpers and views listed in *Sources* — zero **`create`** / **`new`** / `find_or_*` call sites anywhere in the application.

The Sentry backfill that would populate historical receipts, [HK-479](https://linear.app/newbuilds/issue/HK-479), is in **Backlog**. **Practical consequence for staff:** until HK-474 / HK-475 ship, an empty Orders Overview means *"nothing has been recorded"*, **not** *"no orders arrived"* — the absence of a row is not evidence about the order flow.

## The data layer — three audit tables
All three landed in [HK-473](https://linear.app/newbuilds/issue/HK-473) · PR [#14188](https://github.com/marketertechnologies/marketer/pull/14188). Enum values below are read from the models at tag `v1.376.0` — with one exception, `skip_reason`, called out below.
- **Campaign Order Intake Receipt** (`campaign_order_intake_receipts`, model `CampaignOrderIntakeReceipt`) — *one row per intake attempt* across the Vitec webhook, the Webtop webhook and the M360 portal mutation. A row is written `pending` on entry and updated on exit. `source`: `webhook_vitec` · `webhook_webtop` · `portal_m360`. `outcome`: `pending` · `accepted` · `rejected`. `rejection_stage` (8 values, telling staff *where* intake gave up): `auth` · `resource_validation` · `broker_resolution` · `duplicate` · `facade` · `unhandled_error` · `authorization` · `attributes`. `origin_hint`: `auto` · `manual` — whether the order looks like it was triggered by our own auto-order pipeline or by a human. Carries the CRM identifiers (`installation_id`, `estate_id`, `case_id`, `external_order_id`, `department_id`, `flow_base_url`), the resolved `company_id` / `campaign_package_id` / `campaign_package_instance_id`, and a `sentry_event_id` reserved for the [HK-479](https://linear.app/newbuilds/issue/HK-479) backfill.
- **Vitec Auto Order Attempt** (`vitec_auto_order_attempts`, model `Vitec::AutoOrderAttempt`) — *one row per pipeline stage per Sidekiq attempt* on the outbound leg. `stage`: `crm_gateway_received` (0) · `checklist_pushed` (1) · `orders_fetched` (2) · `order_status_fetched` (3) · `order_processed` (4). `status`: `succeeded` · `failed` · `skipped`. `phase`: `for_sale` · `coming_for_sale`. Also records `sidekiq_attempt`, `http_status`, `error_class` / `error_message`, and a `skip_reason` **free-text column** whose intended stage-0 vocabulary — `not_second_hand` · `not_synced_from_vitec` · `phase_timing` · `not_listed` · `no_product_ids` — is specified only in [HK-473](https://linear.app/newbuilds/issue/HK-473)'s schema table and is **not** enum-constrained in code at this tag. Corrected 2026-08-31 (independent BE v1.376.0 audit, finding F2 — the values are right, the attribution was not): `db/schema.rb:3478` @ `v1.376.0` declares a plain nullable `t.string "skip_reason"`; `Vitec::AutoOrderAttempt` declares `enum` for `stage`, `status` and `phase` only, and validates presence of `stage` / `status` / `started_at` but never `skip_reason`; and none of the five values appears anywhere under `app/`, `db/`, `config/` or `lib/` at the tag. **Consequence:** [HK-475](https://linear.app/newbuilds/issue/HK-475) (the writer ticket, still *In Review*) can write any string into that column without anything failing, so staff should treat a `skip_reason` they do not recognise as possible drift rather than as an impossible value.
- **Vitec Checklist Push** (`vitec_checklist_pushes`, model `Vitec::ChecklistPush`) — *one row per checklist message pushed to Vitec's CRM*, i.e. the actual outbound PUT. Carries `installation_id`, `estate_id`, `phase`, `existing_home_id`, `pushed_at` and the `tag` written (`ORDER_CAMPAIGN` or `ORDER_CAMPAIGN_KFS`). It is the record that backs the receipt's `origin_hint` heuristic. It gained a `uuid` + unique index in [HK-504](https://linear.app/newbuilds/issue/HK-504) · PR [#14218](https://github.com/marketertechnologies/marketer/pull/14218) purely so it could have a shareable per-push URL.

The pipeline these tables observe is documented on [CRM Gateway](crm-gateway.md) and, journey-side, on the [Flow deep-dive: Broker Experience — CRM Order → Live Ads → Completion on Sale](../user-flows-and-journeys/flow-broker-experience-crm-order.md).

## Orders Overview — the inbound leg

### List (`/admin_panel/orders_overview`)
Columns rendered at the tag: **Received · Source · Client · External Order · Outcome · Origin · Rejection Stage · Events · Details**, newest `received_at` first, 25 per page with a total-count banner ([HK-476](https://linear.app/newbuilds/issue/HK-476) · PR [#14200](https://github.com/marketertechnologies/marketer/pull/14200)).

Rows are **collapsed by order chain**, not one-per-receipt: `CampaignOrderIntakeReceipts::List` groups on `(source, external_order_id)` where an external order id exists, and falls back to the receipt's own `uuid` so a pre-parse rejection never collapses into someone else's chain — one row per order, with the *Events* column showing how many delivery attempts it took ([HK-477](https://linear.app/newbuilds/issue/HK-477) · PR [#14203](https://github.com/marketertechnologies/marketer/pull/14203)).

**Filters** ([HK-476](https://linear.app/newbuilds/issue/HK-476) · PR [#14200](https://github.com/marketertechnologies/marketer/pull/14200)): Source · Client (company) · Outcome · Rejection stage · Origin · Received-from / Received-to dates. All compose with AND; blanks are no-ops.

**Search** ([HK-500](https://linear.app/newbuilds/issue/HK-500) · PR [#14213](https://github.com/marketertechnologies/marketer/pull/14213)) — one free-text field, deliberately single rather than several dropdowns, because *"operators arriving from Sentry / support tickets have some identifier — they don't know which column it belongs to."* It is a case-insensitive `ILIKE '%q%'` fanned out with `OR` across `external_order_id`, `installation_id`, `estate_id`, `case_id`, `department_id`, `sentry_event_id`, and (cast to text, so a partial UUID matches) `uuid`, `campaign_package_uuid`, `broker_uuid`, `existing_home_uuid` — **plus three LEFT-JOINed resource names**: `campaign_packages.name`, `brokers.name` and `existing_homes.estate_id`. LEFT JOIN is the point: a receipt whose `broker_uuid` points at something that was never persisted (rejected before resolution) still surfaces on its uuid substring. Input is `sanitize_sql_like`-escaped so a typed `%` or `_` is literal, and the search AND-composes with every other filter.

### Drill-down (`/admin_panel/orders_overview/:uuid`)
Opened from *Details*. Four sections ([HK-477](https://linear.app/newbuilds/issue/HK-477) · PR [#14203](https://github.com/marketertechnologies/marketer/pull/14203); fourth section [HK-498](https://linear.app/newbuilds/issue/HK-498) · PR [#14206](https://github.com/marketertechnologies/marketer/pull/14206)):
1. **Header card** — the order's identifiers, source / origin / outcome badges, client, and the resulting **Campaign Package Instance** if intake got that far.
2. **Sibling receipts** — every delivery attempt in the same order chain, chronologically, each with its outcome and (when rejected) its rejection stage and reason. Grouping is `(source, external_order_id)`, falling back to `(installation_id, estate_id)` bounded to **±24 h** around the anchor's `received_at` so unrelated orders for the same property do not collide.
3. **Auto-Order Pipeline** — the `Vitec::AutoOrderAttempt` rows for the same order, i.e. the outbound work that most likely *caused* this inbound callback. Matched on `external_order_id` when known, else the same `(installation_id, estate_id)` ±24 h fallback.
4. **Checklist Pushes** — the `Vitec::ChecklistPush` rows for the same property within ±24 h, with Pushed At, Phase, Tag, Installation, Estate and a link to the Existing Home. `Vitec::ChecklistPush` has no `external_order_id`, so this join is *always* the `(installation_id, estate_id)` + window one, and returns nothing when the anchor is a portal receipt with neither identifier ([HK-498](https://linear.app/newbuilds/issue/HK-498) · PR [#14206](https://github.com/marketertechnologies/marketer/pull/14206)).

Empty sections are handled explicitly rather than shown as blank tables ([HK-504](https://linear.app/newbuilds/issue/HK-504) · PR [#14218](https://github.com/marketertechnologies/marketer/pull/14218)). Every resource reference on the page is a hyperlink rendered through a shared `labeled_resource_text` helper in the uniform shape `<Type> #<id> (<friendly name>)` ([HK-477](https://linear.app/newbuilds/issue/HK-477) · PR [#14203](https://github.com/marketertechnologies/marketer/pull/14203)).

## Auto Order Attempts — the outbound leg

### List (`/admin_panel/auto_order_attempts`)
Columns at the tag: **First started · Last started · Phase · Company · Existing Home · Stage reached · Status · Stages · Details** ([HK-501](https://linear.app/newbuilds/issue/HK-501) · PR [#14215](https://github.com/marketertechnologies/marketer/pull/14215); grouped form [HK-502](https://linear.app/newbuilds/issue/HK-502) · PR [#14216](https://github.com/marketertechnologies/marketer/pull/14216)).

The list shows **one row per pipeline run, not per attempt**: `Vitec::AutoOrderAttempts::GroupedList` partitions by `(installation_id, estate_id, phase, DATE(started_at))` and surfaces the **furthest stage reached** in that group, with first/last timestamps and a stage count — so a retry storm reads as one row you can open, not fifty rows you must correlate ([HK-502](https://linear.app/newbuilds/issue/HK-502) · PR [#14216](https://github.com/marketertechnologies/marketer/pull/14216)).

**Filters:** Stage · Status · Phase · Company · Started-from / Started-to, plus the same single free-text **Search** shape as Orders Overview ([HK-501](https://linear.app/newbuilds/issue/HK-501) · PR [#14215](https://github.com/marketertechnologies/marketer/pull/14215), search shape after [HK-500](https://linear.app/newbuilds/issue/HK-500) · PR [#14213](https://github.com/marketertechnologies/marketer/pull/14213); *Existing Home ID* and the skip-reason / error-class inputs were folded into that one Search field by [HK-504](https://linear.app/newbuilds/issue/HK-504) · PR [#14218](https://github.com/marketertechnologies/marketer/pull/14218) — see *Known gaps* #2).

### Group drill-down (`/admin_panel/auto_order_attempts/details`)
Reached from *Details*; addressed by the group handle `installation_id` + `estate_id` + `phase` + `started_on` rather than by a single record's uuid ([HK-502](https://linear.app/newbuilds/issue/HK-502) · PR [#14216](https://github.com/marketertechnologies/marketer/pull/14216)). It renders, for that property / phase / day: the **full stage chain** in stage order with each Sidekiq attempt, the **checklist pushes** made in the same window, the **resulting Campaign Package Instance**, and the **matching intake receipt** — the inverse join back to Orders Overview, resolved from the group's `external_order_id`s and preferring a `webhook_vitec` receipt over `webhook_webtop` over `portal_m360`, then the earliest `received_at`.

**Reading the chain is the point of the screen** — the interpretation guide from the ticket ([HK-502](https://linear.app/newbuilds/issue/HK-502)): all stages green → happy path; chain ends at a stage-0 *skip* → the property was ineligible, read `skip_reason`; ends at stage 1 *failed* → the PUT to Vitec broke, read `http_status` + `error_message`; ends at stage 2 with no orders → Vitec accepted the tag but produced nothing; ends at stage 3 *failed* → the order exists in Vitec but we cannot read its state. And **the absence of a matching receipt is itself the signal**: it means Vitec never called back for this pipeline.

### Per-attempt show (`/admin_panel/auto_order_attempts/:uuid`)
A single attempt's full record — stage / status / phase badges, Sidekiq attempt, started / finished, HTTP status, skip reason or error class + message, and links to Company, Existing Home and Campaign Package Instance ([HK-502](https://linear.app/newbuilds/issue/HK-502) · PR [#14216](https://github.com/marketertechnologies/marketer/pull/14216)).

## Checklist Push show page
`/admin_panel/checklist_pushes/:uuid` — a single card with the push's uuid, Pushed at, Phase badge, Tag, Installation, Estate, a link to the Existing Home, and created/updated timestamps. There is **no index and no back-navigation**: the page exists only to give a push a **stable, shareable URL** that staff can paste into a ticket, reached from the Details column of the two places pushes are already listed (the Orders Overview drill-down's Checklist Pushes section and the Auto Order Attempts group drill-down) ([HK-504](https://linear.app/newbuilds/issue/HK-504) · PR [#14218](https://github.com/marketertechnologies/marketer/pull/14218)).

## Charts (Chartkick + Groupdate)
Both panels carry two time-series charts above the table so staff *"see the current filter's shape at a glance before drilling into the table"* ([HK-478](https://linear.app/newbuilds/issue/HK-478) · PR [#14220](https://github.com/marketertechnologies/marketer/pull/14220)). `chartkick` (~5.0) and `groupdate` (~6.4) were added to the Gemfile and wired into the **admin** layout only, so no public page loads the charting JS ([HK-478](https://linear.app/newbuilds/issue/HK-478) · PR [#14220](https://github.com/marketertechnologies/marketer/pull/14220)).
- **Orders Overview** — *Volume by day, one series per source* (`webhook_vitec` / `webhook_webtop` / `portal_m360`), plus a per-source totals strip above it, and *Rejections by client* (top 10 companies by rejected receipts, ties broken by company name) ([HK-478](https://linear.app/newbuilds/issue/HK-478) · PR [#14220](https://github.com/marketertechnologies/marketer/pull/14220)).
- **Auto Order Attempts** — *Volume by day, one series per status* (`succeeded` / `failed` / `skipped`) with a per-status totals strip, and *Failures by client* (top 10 companies by failed attempts) ([HK-508](https://linear.app/newbuilds/issue/HK-508) · PR [#14221](https://github.com/marketertechnologies/marketer/pull/14221)).

Both chart pairs honour the panel's active filters. **Two deliberate asymmetries staff should know about:** (i) when no date filter is set the charts fall back to a **last-30-days** window while the table below them does not, so the chart totals and the table's total-count banner can legitimately disagree — the window in force is printed in each chart's heading ([HK-478](https://linear.app/newbuilds/issue/HK-478) · PR [#14220](https://github.com/marketertechnologies/marketer/pull/14220); see *Known gaps* #3); and (ii) on Auto Order Attempts the charts count **individual attempts** while the table shows **grouped runs**, which is the ticket's stated intent — *"one retry chain is many attempts, and that's what the volume view should reflect"* ([HK-508](https://linear.app/newbuilds/issue/HK-508)).

## Known gaps & candidate bugs (code-vs-intent — FLAGGED, not silently reconciled)
Each is a **PO / owner question**, not a settled contract. Code = how it *does* behave; these are where the shipped code diverges from, or outruns, the written ticket. **None of these has been filed anywhere** — they are drafts raised to the operator by the BE v1.376.0 sync.

1. **⚠️ The panels have no data source at this tag — staged, but the staging is not visible from the screens.** *Intent* ([HK-473](https://linear.app/newbuilds/issue/HK-473)): writes land in Tickets 2 and 3. *Actual* (code @ `v1.376.0`): [HK-474](https://linear.app/newbuilds/issue/HK-474) and [HK-475](https://linear.app/newbuilds/issue/HK-475) are still *In Review*, so both panels ship to production reachable, sidebar-linked and permanently empty. Nothing in the UI distinguishes "no receipts recorded because collection has not started" from "no orders arrived" — an empty-state notice would. **Not a code-vs-ticket divergence; a delivery-sequencing gap with a real mis-read risk for staff.**
2. **⚠️ Auto Order Attempts ships three fewer filters than [HK-501](https://linear.app/newbuilds/issue/HK-501) specifies.** *Intent* (HK-501's filter table): Stage, Status, Phase, Company, **Existing home ID**, **Skip reason** (ILIKE), **Error class** (ILIKE), Search, and the two date bounds. *Actual* (`AutoOrderAttemptsController#filter_params` @ `v1.376.0`): only `stage`, `status`, `phase`, `company_id`, `q`, `started_at_from`, `started_at_to` are permitted. The three missing ones were **deliberately folded into the single Search field** by a later commit in [HK-504](https://linear.app/newbuilds/issue/HK-504) · PR [#14218](https://github.com/marketertechnologies/marketer/pull/14218) (*"Fold Existing Home ID + Reason filters into Search"*), which is a defensible UI call — but HK-501 is marked *Done* with its filter table unamended, so **the ticket and the screen disagree**. Also worth confirming: Search fans out over `installation_id` / `estate_id` / `external_order_id` / `uuid` / joined `existing_homes.estate_id`, so an operator who previously filtered by *skip reason* or *error class* now has no exact-match route to those columns at all.
3. **⚠️ Charts and table can legitimately disagree, and [HK-478](https://linear.app/newbuilds/issue/HK-478) asks for both.** The same ticket specifies *"Default date window when no `received_at_from` is passed: last 30 days"* **and**, in its Definition of Done, *"charts … stay consistent with the table's count total."* The code implements the former (`chart_scope` injects a 30-day lower bound; the table's scope does not), so with no date filter set the two figures differ by design. The heading prints the window, which mitigates it. **Internally inconsistent ticket, resolved in code toward the 30-day default — flagging the ticket, not the code.**
4. **⚠️ [HK-502](https://linear.app/newbuilds/issue/HK-502) specifies a drill-down that was not the one built.** *Intent*: a `show` action keyed on the attempt's `uuid`, backed by a `Vitec::AutoOrderAttempts::LoadBundle` interactor, with the sibling chain resolved over `(existing_home_id, phase)` within **±24 h**, a single `checklist_push`, and a `matching_receipt` restricted to `source: webhook_vitec` and tie-broken by *earliest `received_at` after the anchor*. *Actual* (code @ `v1.376.0`): `show` renders **one attempt only**; the chain lives on a separate `details` **collection** action keyed on `(installation_id, estate_id, phase, started_on)` and bounded to a **single calendar day** rather than ±24 h; there is **no `LoadBundle` service**; checklist pushes are a **collection** (day ± 1 h), and the matching receipt is resolved from the group's `external_order_id`s across **all three sources** in a `webhook_vitec → webhook_webtop → portal_m360` preference order. The shipped design is arguably better (it matches the grouped list), but it is materially different from the *Done* ticket, and the **window semantics differ in a way that changes results**: a pipeline that starts at 23:50 and retries at 00:10 falls into two different calendar-day groups, where ±24 h would have kept it together.
5. **⚠️ Two ticket-specified fields cannot exist, because the column does not.** [HK-502](https://linear.app/newbuilds/issue/HK-502) (Section 3) and [HK-504](https://linear.app/newbuilds/issue/HK-504) (View) both list **HTTP status** among the `Vitec::ChecklistPush` fields to render, but `vitec_checklist_pushes` has no `http_status` column in [HK-473](https://linear.app/newbuilds/issue/HK-473)'s schema and none was added — the shipped show page correctly omits it (verified in `app/views/admin_panel/checklist_pushes/show.html.erb` @ `v1.376.0`). The HTTP status of the outbound PUT is recoverable only from the paired stage-1 `Vitec::AutoOrderAttempt`. **Stale ticket text, not a code defect** — but it means the push record alone cannot answer "what did Vitec reply?".
6. **⚠️ The sidebar's default-window behaviour was reversed against the ticket, on purpose.** [HK-501](https://linear.app/newbuilds/issue/HK-501) specifies the nav link as `admin_panel_auto_order_attempts_index_path(started_at_from: Date.yesterday)`, *"Default filter to yesterday for the same rationale as Failed Campaigns — keep the initial page snappy."* The shipped link passes **no date parameter** (commit *"Drop default date filter from admin panel nav links"*, [HK-501](https://linear.app/newbuilds/issue/HK-501) · PR [#14215](https://github.com/marketertechnologies/marketer/pull/14215)), so both new panels open on **all history**. This is the same shape as *Known gaps* #8 on the [Failed Campaigns Admin Dashboard](failed-campaigns-admin-dashboard.md) — worth deciding once, consistently, across the admin panel.
7. **Open question — search performance is knowingly unindexed.** [HK-500](https://linear.app/newbuilds/issue/HK-500) states it outright: substring `ILIKE '%q%'` cannot use a B-tree index, no trigram (`pg_trgm`) coverage was added, and *"a seq scan on a few million rows is acceptable through the panel's paginator."* The same fan-out now also runs on Auto Order Attempts. Untested against real volume, because there is no real volume yet (*Known gaps* #1).
