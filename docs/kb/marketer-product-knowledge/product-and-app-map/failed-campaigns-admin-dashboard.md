## What it is
An **internal back-office tool for Marketer staff** (CSMs / support / ops) to triage, diagnose, and repair campaigns whose ad-platform **publication has failed**. It surfaces the campaigns needing human attention and gives one-click access to repair / republish actions plus deep-links into every relevant surface. The author framed it as "an evolved version of what we had in Metabase."

It is part of the **Admin Panel** (see the *Admin Panel* row in <mention-page url="https://app.notion.com/p/39614549bf5f8152a955e98fb5158d64">Product & App Map</mention-page>) and is a **Rails (M2 `marketer` repo) Administrate-style page — NOT the M360 React SPA.** A grep of `marketer-frontend` `development` found no failed-campaigns dashboard, no `manual_repair`, and no `FailedCampaign*` component; G3/G6 below are Rails ERB views.
- **List / dashboard:** `/admin_panel/failed_campaigns`
- **Per-campaign detail:** the admin campaign show page `/admin_panel/campaigns/:id`
- **Entry point:** a per-company "failed campaigns" link on the company admin page (the demo opened it from a company with none, then went to the all-failed-campaigns page).
- **Built by:** [marketer#14063](https://github.com/marketertechnologies/marketer/pull/14063) (HK-196, merged 2026-07-06 @ `c0630b6fb0`). Requires the admin panel to be mounted (review-app / `HEROKU_PR_NUMBER` context).

## Who uses it
**Marketer staff — CSMs, support, ops.** Not customer users. (Same audience as the Admin Panel generally.)

## The dashboard (list page)
One table of currently-failing campaigns.
- **Prefilter to the last 24 hours** — the demo shows the dashboard opening pre-filtered to the last 24 h of failures (removable / adjustable; demo 00:01:19). ⚠️ **QA (2026-07-14) found the code applies no such default** — with no params the list shows *all* history (see *Known gaps* #8).
- **Per-row content** (demo 00:01:19–00:03:37, 00:08:23–00:09:35):
	- **Company name.**
	- **Campaign name** → the admin view of the campaign.
	- **Promotable** — the name is a link; for **existing homes the name is always the address** (so there is *no separate address column*). It leads to the property in M360, or to the **broker page** in M360 for a broker; the name also links to the promotable's admin page.
	- **Type** — *broker promotion* or *sale*.
	- **Enabled channels** as clickable links to the provider's page; each is **outlined red if that channel's publication failed**. A non-active channel button = no publication happened → no link.
	- **M360 / Broker-Experience deep-link "shortcut" badges** (the pale-red boxes) — convenience links so staff don't hand-build URLs.
	- **Assignment** — assign yourself (or any admin) to a failed campaign inline, so no one else picks it up.
	- **Last admin comment** — a preview of the most recent comment is shown in the table.
	- **"Requires Manual Repair"** indicator (see below).
- **Filters:** by **company** and by **campaign type**; more to be added as needed.

## "Requires Manual Repair" — the core concept (demo 00:03:37–00:04:56)
- A periodic **auto-repair job runs every ~30 minutes** and tries to fix failed campaigns automatically. After a set number of **retries** all fail, the campaign is marked **requires manual repair** — the terminal "auto-repair exhausted, a human is needed" state.
- **Intended:** ideally staff should *only* see campaigns that require manual repair. A **blank** (not-marked) row means the auto-repair job may still fix it — *"a chance, not a guarantee."*
- **Origin:** [MT3-9418](https://marketer.atlassian.net/browse/MT3-9418) (extend the periodic retry across channels for a whitelist of known errors) → refactored into a per-campaign repair flow that introduced the terminal `requires_manual_repair_at` state ([#13980](https://github.com/marketertechnologies/marketer/pull/13980); MT3-9467/86/87).
- **Future (not built):** Slack notifications when a campaign needs manual repair — especially zip-code failures, which can only be fixed manually.

### Known auto-repair categories (matchers) — added v1.150.0
Before a failed campaign reaches the terminal *requires-manual-repair* state, the auto-repair job matches it against a registry of **known failure categories** ("matchers"); a match triggers an automatic repair action, so only failures with no known matcher fall through to manual triage. **v1.150.0** ([HK-270](https://linear.app/newbuilds/issue/HK-270) · PR [#14110](https://github.com/marketertechnologies/marketer/pull/14110) · code @ `ada4c223`) added **three campaign-level matchers**, each recovering one known publication failure:
- **Snapchat — stale creative:** the most-recent publication on a Snapchat channel failed with an error message containing *"refers to a non-existent creative"* ([HK-270](https://linear.app/newbuilds/issue/HK-270) · [#14110](https://github.com/marketertechnologies/marketer/pull/14110)).
- **Publishing service — invalid object:** the most-recent publication (any channel) failed with error class `PublishingService::Presenters::InvalidObjectError` ([HK-270](https://linear.app/newbuilds/issue/HK-270) · [#14110](https://github.com/marketertechnologies/marketer/pull/14110)).
- **DV360 — asset-download failure:** the most-recent publication on a GMP/DV360 channel failed with an error message containing *"Unable to download asset"* ([HK-270](https://linear.app/newbuilds/issue/HK-270) · [#14110](https://github.com/marketertechnologies/marketer/pull/14110)).

All three run the shared **Regenerate & Republish** repair action: it re-enqueues `PrepareCampaignJob` (with `for_republish`) and then `RepairPublicationJob` for the campaign's **enabled** channels; a campaign with no enabled channels is a no-op ([HK-270](https://linear.app/newbuilds/issue/HK-270) · [#14110](https://github.com/marketertechnologies/marketer/pull/14110)). Being **campaign-level** matchers they take **full ownership** of the repair — the per-publication matchers are skipped once one matches — and allow **one** automatic retry (`MAX_RETRIES = 1`); if that retry also fails the campaign is stamped *requires manual repair* as described above ([HK-270](https://linear.app/newbuilds/issue/HK-270) · [#14110](https://github.com/marketertechnologies/marketer/pull/14110)).

*Added by the v1.150.0 KB sync (<mention-date start="2026-07-23"/>) — pending operator gate. Intent per [HK-270](https://linear.app/newbuilds/issue/HK-270); code confirmed in PR [#14110](https://github.com/marketertechnologies/marketer/pull/14110) (merge `ada4c223`, read-only). ## Global (bulk) actions — list page (demo 00:04:56–00:08:23)
Hidden behind a reveal to discourage over-clicking. Each action carries a **description of what it does**; republish actions show an **estimated run time** (≈8 s delay × number of campaigns, to avoid overwhelming provider APIs).
- **Try Repair Campaigns** — runs the repair job *now*; shows a **countdown** to the next automatic run. Safe to click even if it's about to run (**job uniqueness → no double-schedule**); pointless if everything is already marked requires-manual.
- **Republish All Failed Publications** — the **preferred** bulk action (republishes only the *failed* channel publications).
- **Republish All Failed \<Channel\>** (e.g. Facebook) — for channel-specific incidents / provider maintenance windows.
- **Republish All** — republishes **everything, including already-successful channels** → **discouraged**, guarded by a **confirmation popup**.
- **⚠️ Hard restriction (stated in every job's description):** these bulk jobs act **only on campaigns that failed in the last 24 hours**, even if the page is configured to show full history (which can be thousands). Making the window configurable is a stated future.

## Campaign detail (admin campaign show page) (demo 00:09:35–00:11:16)
Same structure; **per-campaign repair actions**:
- **Regenerate** — a heavy, multi-step action (full description shown in the UI).
- **Try to Repair** — the single-campaign slice of the 30-minute repair job.
- **Republish All** — all channels incl. successful; discouraged.
- **Republish Failed Channels** — only the channels with a red dot (failed).
- **Full publication errors are visible HERE** (the campaign page), not in the dashboard table — the table deliberately does **not** preload errors (too much data). Josep asked for errors in the table; the answer was "see the campaign page." ([MT3-9353](https://marketer.atlassian.net/browse/MT3-9353) "Always show the full publication error for Admins.")
- **Publication links & details** (clickable through to the publication), **assignment** (any admin), **M360 links**.
- **Comments:** full history with pagination; add comments; **delete is only on the comment *edit* page** (deliberately not on the main view, to prevent accidental deletion).

### Action / job states (demo 00:11:16–00:13:49)
- A **running** repair/republish job → the button shows *"running"* and is **disabled**.
- **Regenerate running** → shows *"pending batch"*; the button **stays enabled** because some campaigns can remain silently marked *pending regeneration* if regenerate failed.
- **Feature-disabled state:** the failed-campaigns repair job can be turned off (rarely seen).

## Failed-publication visibility & filtering (Publications admin) — added v1.373.0
*Release sync 2026-08-11 — pending operator gate. Intent per [HK-422](https://linear.app/newbuilds/issue/HK-422); every item below confirmed against the merged diff of PR [#14163](https://github.com/marketertechnologies/marketer/pull/14163) (merge `80434144`).*

The stated goal is **better visibility into failed campaign publications, so staff can diagnose and respond to publication errors faster** ([HK-422](https://linear.app/newbuilds/issue/HK-422)). Five changes shipped, spanning the campaign show page, the **Channels/Publications** admin page, and the **auto-republishable error** page:
- **Conditional "Requires Manual Repair" badge** — the badge on the admin **campaign show** page now renders only when `requires_manual_repair_at` **and** `publish_failed_at` are both present; previously any `requires_manual_repair_at` timestamp showed it, including on campaigns that were no longer failing. This is the fix the team agreed on in the 2026-07-08 demo — see *Known gaps* #1 ([HK-422](https://linear.app/newbuilds/issue/HK-422) · [#14163](https://github.com/marketertechnologies/marketer/pull/14163)).
- **Filters on the Channels/Publications page** — a new `AdminPanel::Publications::List` service filters by **Status** (`scheduled` / `in_progress` / `succeeded` / `failed`), **Channel type** (multi-select, options derived from `Channel.types`), and **Error message** (a `contains` match — `ILIKE` against the JSONB `error ->> 'message'`). Blank filters are no-ops; an unrecognised channel type is ignored rather than returning nothing ([HK-422](https://linear.app/newbuilds/issue/HK-422) · [#14163](https://github.com/marketertechnologies/marketer/pull/14163)).
- **Error-message column** on that table — backed by a virtual `Channels::Publication#error_message` that returns `error['message']` **only when `error` is a Hash**, so a nil or non-hash `error` renders blank instead of raising ([HK-422](https://linear.app/newbuilds/issue/HK-422) · [#14163](https://github.com/marketertechnologies/marketer/pull/14163)).
- **"Latest Incidents" link** on the **auto-republishable error** show page — jumps to the Publications page pre-filtered to status `failed` **+** that error's message, sorted by `failed_at` **descending**, so staff land on the most recent occurrences of exactly that error. *(Scope note: the ticket asked for status + error message; the shipped link also passes the channel types configured on the error — additive to the AC, confirmed in the diff.)* ([HK-422](https://linear.app/newbuilds/issue/HK-422) · [#14163](https://github.com/marketertechnologies/marketer/pull/14163)).
- **Enabled Channels table** on the admin campaign show page — one row per enabled channel: channel type (linked to its typed admin path, e.g. `/admin_panel/channels/facebooks/:id`), external ID, **phase** badge (`not_published` / `published` / `paused` / `archived`), and a link to that channel's latest publication (an em-dash when it has none). The whole section is omitted when the campaign has no enabled channels ([HK-422](https://linear.app/newbuilds/issue/HK-422) · [#14163](https://github.com/marketertechnologies/marketer/pull/14163)).

Supporting mechanism (not user-visible, but it governs how the filters behave): dashboards may now declare `EXTRA_PERMITTED_PARAMS`, and `AdminPanelHelper#sanitized_order_params` merges them into Administrate's sort links. Without it Administrate's hardcoded permit list silently dropped the custom filter params, so **clicking a column header reset the filters** ([HK-422](https://linear.app/newbuilds/issue/HK-422) · [#14163](https://github.com/marketertechnologies/marketer/pull/14163)).

> ⚠️ **Does not close *Known gaps* #6.** The error-message column lands on the **Channels/Publications** page, *not* on the failed-campaigns dashboard table where Josep's request (MT3-9353) sat. Errors are still absent from the dashboard's own table — gap #6 stands as written.

## Content-incomplete campaigns & the publish circuit breaker — added v1.377.0
*Release sync 2026-09-01 (BE v1.377.0, commit `ac0c0f1`) — pending operator gate. Intent per [HK-509](https://linear.app/newbuilds/issue/HK-509) and [HK-503](https://linear.app/newbuilds/issue/HK-503); every item below confirmed against the merged diffs of PR [#14222](https://github.com/marketertechnologies/marketer/pull/14222) (merge `cb5143ea`) and PR [#14219](https://github.com/marketertechnologies/marketer/pull/14219) (merge `244889f2`), read at tag `v1.377.0`, read-only.*

Two things change for staff on this dashboard. First, a campaign can now appear here for a **second reason** — it had *nothing to publish*, as distinct from a publication that *failed*. Second, a campaign whose publish keeps failing is now **parked automatically** after a bounded number of attempts, and there is a new operator action to release it.

### 1 · A campaign with no content is now "content incomplete", not "publish failed"
The [HK-471](https://linear.app/newbuilds/issue/HK-471) front-door guard (see *Publication / Publish* in the Glossary) raises `Campaigns::Publish::NoPublishableContentError` when a campaign has zero creative sets. Until this release that error was rescued as a generic `Publish::Error` and stamped `publish_failed_at`. It is now classified separately ([HK-509](https://linear.app/newbuilds/issue/HK-509) · [#14222](https://github.com/marketertechnologies/marketer/pull/14222)):
- **New marker column** `campaigns.content_incomplete_at` (+ index), migration `20260824120000_add_content_incomplete_at_to_campaigns.rb`.
- **Rescue split** in `Campaigns::PublicationJob` and `Campaigns::RepairPublicationJob`: `NoPublishableContentError` stamps `content_incomplete_at`, leaves a `campaign content incomplete` monitoring breadcrumb, and **does not re-raise** (the 5-minute cadence re-drives regeneration). Any other `Publish::Error` still stamps `publish_failed_at` and re-raises, unchanged.
- **A successful publish clears both markers** — `Campaigns::Publish#prepare_campaign` now nils `content_incomplete_at` alongside `publish_failed_at`.
- `content_incomplete_at` is exposed on the GraphQL `CampaignType`.

**Why (intent, [HK-509](https://linear.app/newbuilds/issue/HK-509)):** an incomplete campaign *never attempted* to publish, so stamping `publish_failed_at` is *"a category error that pollutes the failed-campaigns signal and the repair scope"*. Separating the two means retry is never gated on a failure marker.

### 2 · What that changes on this dashboard
- **The roster broadened.** A new `Campaign.content_incomplete_campaigns` scope (`content_incomplete_at` present, has a campaign package, phase in `scheduled` / `live`) is unioned into the list: `AdminPanel::FailedCampaigns::List#base_scope` is now `failed_auto_campaigns.or(content_incomplete_campaigns)`. The dashboard is therefore no longer "failed campaigns" only ([HK-509](https://linear.app/newbuilds/issue/HK-509) · [#14222](https://github.com/marketertechnologies/marketer/pull/14222)).
- **New "Status" column** on the list table: a red *Publish failed* badge when `publish_failed_at` is present, an amber *Content incomplete* badge when only `content_incomplete_at` is. The two are mutually exclusive in the view — `publish_failed_at` wins the conditional ([HK-509](https://linear.app/newbuilds/issue/HK-509) · [#14222](https://github.com/marketertechnologies/marketer/pull/14222)).
- **The date column** now renders `publish_failed_at || content_incomplete_at`, and the controller orders the list by `COALESCE(content_incomplete_at, publish_failed_at) DESC` ([HK-509](https://linear.app/newbuilds/issue/HK-509) · [#14222](https://github.com/marketertechnologies/marketer/pull/14222)).

### 3 · The publish circuit breaker — a bounded number of attempts, then park
[HK-503](https://linear.app/newbuilds/issue/HK-503) closes the loop the reverted [HK-481](https://linear.app/newbuilds/issue/HK-481) exposed: three drivers re-attempted publish with no shared cap, and the existing "give up" flag `requires_manual_repair_at` was honoured by only one of them (the repair job), so the two 5-minute drivers in `ProgressRunningCampaigns` looped forever ([HK-503](https://linear.app/newbuilds/issue/HK-503) · [#14219](https://github.com/marketertechnologies/marketer/pull/14219)):
- **The park flag is now universal.** `can_be_autopublished?` and `can_be_republished?` both return false when `requires_manual_repair_at` is present, so a parked campaign is excluded from *every* driver, not just the repair job.
- **The breaker.** Before autopublishing or republishing, `ProgressRunningCampaigns` counts the campaign's consecutive **failed** publish transitions — types `autopublish`, `republish`, `autopublish_complete`, `republish_complete`, walked newest-first, the streak ending at the first transition with no `failed_at` or a gap of more than 24 h (`STREAK_GAP_LIMIT`) between two consecutive failures. At `PUBLISH_FAILURE_THRESHOLD = 5` (matching the pre-existing `TERMINATE_FAILURE_THRESHOLD`) it stamps `requires_manual_repair_at`, notifies `RepeatedPublishFailure` at severity `error` with the streak metadata, and stops progressing that campaign for the tick.
- **Self-heal.** Below the threshold the campaign keeps auto-regenerating and republishing on the 5-minute cadence; a later success writes a transition with no `failed_at`, which breaks the streak.
- **The streak is campaign-level**, so it unifies autopublish and republish attempts for one campaign rather than counting each driver separately.

### 4 · New staff action — "Unpark"
A row marked *Requires Manual Repair* now carries an **Unpark** button beside the timestamp badge, posting to `POST /admin_panel/failed_campaigns/:id/unpark` → the new `AdminPanel::FailedCampaigns::Unpark` service. It ([HK-503](https://linear.app/newbuilds/issue/HK-503) · [#14219](https://github.com/marketertechnologies/marketer/pull/14219)):
1. clears `requires_manual_repair_at`, returning the campaign to all three drivers; **and**
2. **resets the failure streak** by writing a synthetic `CampaignPackages::SequenceTransition` — type `autopublish_complete` for an assembly campaign, `republish_complete` otherwise — stamped `transitioned_at: Time.current`, `context_data: { manual_unpark: true }` and **no** `failed_at`.

Step 2 is load-bearing, not bookkeeping: clearing the park flag alone would let the breaker re-park the campaign on the very next tick, because the historical failures are still the most recent publish transitions on record. The synthetic success moves the streak cursor so the count restarts at zero. Confirmation flash: *"Campaign unparked for manual repair."*

> **Scope note — which transitions the streak counts (not a divergence).** [HK-503](https://linear.app/newbuilds/issue/HK-503) specifies reusing `consecutive_failed_transitions` for the **`schedule_autopublish`** / **`schedule_republish`** transitions, and the ticket itself names this the *"load-bearing risk to verify first: whether `schedule_autopublish` / `schedule_republish` transitions get `failed_at` written back on downstream failure"*. The merged code counts the **execution and completion** transitions instead, because — per its own comment — the failure write-back lands on those (Prepare raising; `WaitForCreativesJob` timeout; `NoPublishableContentError`) and not on the `schedule_*` wrappers. The ticket asked for the verification; the implementation is its answer. Recorded here so the ticket's literal wording is not read as the shipped rule ([HK-503](https://linear.app/newbuilds/issue/HK-503) · [#14219](https://github.com/marketertechnologies/marketer/pull/14219)).

## Known gaps & candidate bugs (code-vs-intent — FLAGGED, not silently reconciled)
Each is a **PO question**, not a settled contract. Code = how it *does* behave; these are where current code diverges from — or outruns — documented / stated intent.

1. **Stale "Requires Manual Repair" label after a successful repair — team-acknowledged in the demo (00:13:49–00:15:15).** *Intent, agreed by author + PO on the call:* the `requires_manual_repair_at` timestamp is intentionally **kept (never nil'd)** — a fixed campaign is recorded as once-manually-fixed, is no longer auto-repaired, and drops off the failed list — **BUT the *label* should show only when BOTH a failed-publication timestamp AND requires-manual are present** (Mykyta: *"if we have failed publication at timestamp AND require manual, then we show it"*). PO Ovidiu saw the label persist on a campaign he had repaired (*"okay, something is still wrong with this campaign"*). *Current code* shows the label off `requires_manual_repair_at` alone → **candidate bug; fix = gate the label on both timestamps.** *(QA-confirmed live 2026-07-14: show page `show.html.erb:24` gates on `requires_manual_repair_at.present?` alone; a repaired fixture with `publish_failed_at = nil` still shows the red badge while the Try-Repair button is correctly absent. The list-row badge `_campaign_row.html.erb:42` is harmless on the list only because the scope guarantees `publish_failed_at` is set, and it keys on raw presence rather than the `publish_failed?` predicate `publish_failed_at > published_at`.)*

	**✅ Resolved on the campaign show page (v1.373.0, <mention-date start="2026-08-11"/>, pending operator gate):** [HK-422](https://linear.app/newbuilds/issue/HK-422) AC-1 gates the badge on **both** `requires_manual_repair_at.present?` **and** `publish_failed_at.present?` — exactly the rule the author and PO agreed in the demo · PR [#14163](https://github.com/marketertechnologies/marketer/pull/14163). **Scope of the fix, per the diff:** only `app/views/admin_panel/campaigns/show.html.erb` changed; the failed-campaigns **list-row** badge (`_campaign_row.html.erb:42`) was **not** touched and still keys on raw `requires_manual_repair_at` presence — harmless for the reason already noted above (the list scope guarantees `publish_failed_at` is set), and consistent with the ticket, which scoped this AC to the *Campaign Page*. ⚠️ Note the PR *description* claims the badge changed on "campaign show **and failed campaigns** pages"; the merged diff supports only the former.

	**⚠️ The list-row badge's "harmless" argument no longer holds as of BE v1.377.0 (2026-09-01, pending operator gate).** The reasoning recorded twice above — that the un-gated list-row badge is safe *"because the list scope guarantees `publish_failed_at` is set"* — was true only while the list scope was `failed_auto_campaigns` alone. [HK-509](https://linear.app/newbuilds/issue/HK-509) widened it to `failed_auto_campaigns.or(content_incomplete_campaigns)`, and a content-incomplete-only row has `publish_failed_at` **nil** by construction. [HK-503](https://linear.app/newbuilds/issue/HK-503) then made the breaker stamp `requires_manual_repair_at` on exactly such campaigns. So a *Content incomplete* row can now render the red *Requires Manual Repair* badge with no failed-publication timestamp — precisely the state this gap was raised about, on the one page the [HK-422](https://linear.app/newbuilds/issue/HK-422) fix deliberately did not touch. `_campaign_row.html.erb` still keys on raw `requires_manual_repair_at` presence ([HK-509](https://linear.app/newbuilds/issue/HK-509) · PR [#14222](https://github.com/marketertechnologies/marketer/pull/14222); [HK-503](https://linear.app/newbuilds/issue/HK-503) · PR [#14219](https://github.com/marketertechnologies/marketer/pull/14219); code re-read at tag `v1.377.0`).
2. **Manual-repair filter column (G1).** HK-196 wrote *"filter by `requires_manual_repair_at` date/range"*; the shipped date-range filter is on **`publish_failed_at`** (labelled "Failed At From/To"), and `requires_manual_repair_at` is only a **Yes/No/All presence toggle**. One of the two is stale → PO question.

	**Compounded in BE v1.377.0 (2026-09-01, pending operator gate):** `List#filter_by_failed_at` still filters on `publish_failed_at` only, but the list now also carries content-incomplete rows whose `publish_failed_at` is nil. Setting either "Failed At From" or "Failed At To" therefore **silently drops every content-incomplete row** from the results, even though the column those rows display is `content_incomplete_at`. Not addressed by [HK-509](https://linear.app/newbuilds/issue/HK-509), which broadened `base_scope` but left the filters untouched (PR [#14222](https://github.com/marketertechnologies/marketer/pull/14222); code re-read at tag `v1.377.0`).
3. **`requires_manual_repair_at` never cleared on success (G5).** Write-once is **deliberate** (hotfix [#14069](https://github.com/marketertechnologies/marketer/pull/14069) stopped a runaway repair loop), but **no ticket says whether a successful force-repair should clear it.** Currently it never clears → the campaign is **permanently excluded from future automatic repair**. Clear-on-success is undocumented → PO question.

	**✅ Partially resolved — there is now a documented *operator* path to clear it (BE v1.377.0, 2026-09-01, pending operator gate).** [HK-503](https://linear.app/newbuilds/issue/HK-503)'s **Unpark** action (see *Content-incomplete campaigns & the publish circuit breaker* §4 above) clears `requires_manual_repair_at` deliberately and by hand, and additionally resets the failure streak so the breaker does not immediately re-park. This settles the *recovery* half of the gap: permanent exclusion from auto-repair is no longer permanent. **What the gap still asks is unchanged:** whether a *successful* repair/publication should clear the flag **automatically** remains undocumented and unimplemented — the write-once rule from hotfix [#14069](https://github.com/marketertechnologies/marketer/pull/14069) still governs every non-manual path ([HK-503](https://linear.app/newbuilds/issue/HK-503) · PR [#14219](https://github.com/marketertechnologies/marketer/pull/14219)).
4. **Dashboard bulk Global Actions** (Try-Repair / Republish-All / Republish-by-Channel) are **not in HK-196's requirements** (grounded only in the MT3 repair cluster). Confirm they are intended dashboard scope.
5. **Always-both "M360 / BE" badges (G6).** Every row renders **both** an M360 and a **Broker-Experience** deep-link **unconditionally**, even for pure Sale/property campaigns with no broker surface. No ticket mandates this; the demo frames it as an intended convenience shortcut. Confirm the rule (esp. the BE badge on non-broker campaigns). *("BE" = Broker Experience, an M360 surface — not "backend".)*
6. **Errors not shown in the dashboard table** — by design (too much to preload); only on the campaign page. Josep requested table-level error visibility — a future enhancement, not a bug.
7. **Slack notifications** for manual-repair-needed are **not built** (stated future).
8. **No default 24-hour prefilter — QA-confirmed 2026-07-14 (source + live).** The demo says the dashboard *"prefilters for the last 24 hours"*, but the controller applies **no default lower bound** — with no params the list shows **all** failed campaigns across all history (a 5-day-old failure appeared). **Scope trap:** the bulk Global Actions are restricted to last-24 h failures at the *job* level, so an admin can see a >24 h row, click *Republish All Failed*, get a success flash, and that row is silently **not** republished — *visible scope ≠ action scope*. Source: `admin_panel/failed_campaigns_controller#filtered_campaigns` + `list.rb#filter_by_failed_at` (a no-op when the date params are blank). → candidate bug / PO question.

	**A second instance of the same trap arrived in BE v1.377.0 (2026-09-01, pending operator gate).** The list now shows *Content incomplete* rows, but **Try Repair** — both the bulk button and the 30-minute job — still enqueues `Campaigns::RepairFailedCampaignsJob`, whose scope is `Campaign.failed_auto_campaigns.where(requires_manual_repair_at: nil).where(publish_failed_at: 24.hours.ago..)`. That scope was **not** broadened alongside the dashboard's. A staff member can therefore see a *Content incomplete* row, click *Try Repair*, receive the "Repair job has been scheduled" success flash, and that row is silently not repaired — visible scope ≠ action scope, exactly as written above ([HK-509](https://linear.app/newbuilds/issue/HK-509) · PR [#14222](https://github.com/marketertechnologies/marketer/pull/14222); code re-read at tag `v1.377.0`).
9. **"Republish All" is a state-mutating HTTP GET — QA 2026-07-14.** `show.html.erb:78-83` (`method: :get`) + `admin_panel.rb:27` (`get :force_republish`); every *peer* action is POST. Guarded by a `turbo_confirm` dialog and `button_to` (renders a GET `<form>`, not a bare anchor), so crawler-triggering is limited — but it is a REST/CSRF anti-pattern and an inconsistency. Admin-only → low severity.
10. **Minor UX — QA 2026-07-14:** the empty state renders an empty table with **no *"no failed campaigns"* message** (the header count correctly shows `(0)`); and **unassign** is only on the show-page assignment select, not the list row (route `post :unassign` exists but no list control). Spec-silent niceties.
11. **A pre-existing `publish_failed_at` is never cleared when a campaign is re-classified as content-incomplete — added by the BE v1.377.0 sync (2026-09-01, pending operator gate).** *Intent ([HK-509](https://linear.app/newbuilds/issue/HK-509)):* model "content incomplete" **distinctly** from `publish_failed_at`, because "incomplete campaigns never attempted to publish; stamping `publish_failed_at` is a category error that **pollutes the failed-campaigns signal and the repair scope**." *Actual (code @ tag `v1.377.0`):* the content-incomplete rescue path stamps `content_incomplete_at` but never nils `publish_failed_at`. The only place that clears it on this path is `Publish#prepare_campaign`, which is **unreachable** here — `validate_publishable_content!` raises *before* `prepare_campaign` runs. So for any campaign that already carries `publish_failed_at`, both markers end up set at once. *Why this is not a corner case:* before this release `NoPublishableContentError` was a plain `Publish::Error` and fell into the generic rescue, so **the entire pre-existing backlog of zero-content campaigns carries `publish_failed_at` today**. On its next attempt each gains `content_incomplete_at` while keeping `publish_failed_at`, so it stays in `failed_auto_campaigns`, keeps the red *Publish failed* badge (which wins the Status conditional), keeps showing `publish_failed_at` in the date column, and stays in the repair-job scope — while being ordered by `COALESCE(content_incomplete_at, publish_failed_at)`, i.e. by the *other* timestamp. The pollution the ticket set out to remove therefore persists for exactly the population it was written for. The merged specs cover only the fresh case (`publish_failed_at` nil beforehand). → **candidate bug**, raised as a draft to the operator, not filed ([HK-509](https://linear.app/newbuilds/issue/HK-509) · PR [#14222](https://github.com/marketertechnologies/marketer/pull/14222)).
12. **No driver is documented for a scheduled/live content-incomplete campaign — open question, added by the BE v1.377.0 sync (2026-09-01, pending operator gate).** [HK-509](https://linear.app/newbuilds/issue/HK-509) carries an explicit **"OPEN DESIGN DECISION (blocks dispatch)"** with two halves: the *marker* (resolved — an explicit `content_incomplete_at` column shipped) and the *driver* — "Scheduled/live incomplete campaigns need **either** a broadened repair-job scope (include the incomplete marker) **or** the ProgressRunningCampaigns republish trigger." The merged PR broadened the **admin roster** but not `RepairFailedCampaignsJob`'s scope (see #8 above), so regeneration for these campaigns rests entirely on `ProgressRunningCampaigns` — autopublish for assembly campaigns, and for scheduled/live ones only when a republish **trigger** fires (data changed / images changed / end-date update). A scheduled or live content-incomplete campaign with no such trigger has no re-drive path documented anywhere. Which of the two options was chosen is not recorded on the ticket or the PR. → PO question, not asserted as a defect.
13. **Assembly-phase content-incomplete campaigns are invisible on this dashboard — observation, added by the BE v1.377.0 sync (2026-09-01, pending operator gate).** `Campaign.content_incomplete_campaigns` restricts to phase `scheduled` / `live`, mirroring `failed_auto_campaigns`. But the publication jobs stamp `content_incomplete_at` regardless of phase, and [HK-509](https://linear.app/newbuilds/issue/HK-509) discusses **assembly** (never-published) campaigns as a content-incomplete population in its own right. An assembly campaign stamped content-incomplete is therefore driven by autopublish but never surfaces to staff here. This is **consistent with the pre-existing convention** (the failed-campaigns scope has always excluded assembly), so it is recorded as a scope observation and a PO question, **not** as a regression ([HK-509](https://linear.app/newbuilds/issue/HK-509) · PR [#14222](https://github.com/marketertechnologies/marketer/pull/14222); code re-read at tag `v1.377.0`).
