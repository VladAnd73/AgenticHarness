## What CRM Gateway is
A standalone Ruby micro-service that **owns all integration with external real-estate CRMs and hides that complexity from internal clients** (M360/M2, and historically SmartSale). Product framing: *"an internal system responsible for handling integrations with external CRM system and moving heavy lifting from internal clients (e.g. m360) to CRM Gateway"* (Notion — CRM Architecture overview). It is **event-based** (flows composed of atomic events), runs as Heroku worker dynos (Clockwork, Sneakers, Webapp) with its own PostgreSQL + Redis and an S3 + CloudFront CDN for external-CRM assets (ibid.).

It was **extracted from the M2 monolith into its own Rails app** in 2021 (Jira MT-19 — "Move existing CRM code to new Rails application"; MT-222 — CRM architecture proposal). In the KB structure it is a **supporting external service** — see the role entry in [Product & App Map §3](../product-and-app-map.md) and the [Domain Glossary](../domain-glossary.md) "CRM Gateway" / "CRM Configuration" terms; this page is the deep-dive behind them.

## Anatomy of one integration (what "add a CRM" means)
The OBOS epic (MT3-7653, Delivered) — a ~30-story breakdown — is the clearest map of what integrating a CRM entails: on the **gateway** side, an auth-token fetcher, project/estate/image fetchers, representers (project/unit/image/employee/stage/building), responders (fetch-estate, represent-estate, emit-estate-hierarchy) and a scheduler; on the **M2** side, adapters + receivers that persist the emitted hierarchy. Data pulled = estates/projects/stages/units, brokers/employees, images, documents, buyers/leads.

## How M2 consumes CRM Gateway
Two consumption models — the specifics already live in Product & App Map §3 "CRM Gateway", so only the intent + pointers are repeated here:
- **Pub/sub (the main channel)** — *"pub/sub as the main channel"* per the Notion CRM Architecture overview. M2 runs a long-lived subscriber that receives per-origin notifications and persists the estate/broker hierarchy *(code confirms — M2 `app/lib/crm_gateway/subscribe.rb:15`)*.
- **RPC (request/response)** — an on-demand `FetchEstate` pull keyed by company + estate *(code confirms — M2 `app/jobs/crm_gateway/estate_sync_job.rb:8`)*. This is the pull used by the admin re-sync and by the order flow below.

The managed-CRM-sync UI (the "Sync" / re-sync actions) is the product intent behind Jira MT3-8177 (seeded by MT3-431 — "Add control panel for managing CRM integrations through M360").

## How CRM Gateway fits the Vitec/Webtop "order from inside the CRM" flow
**Intent** (Vitec orderflow PRD; Webtop orderflow PRD; delivery epic MT3-8433 — "Vitec orderflow for campaign packages"; KB [Flow deep-dive: Broker Experience — CRM Order → Live Ads → Completion on Sale](../user-flows-and-journeys/flow-broker-experience-crm-order.md)): a broker orders a campaign package for a property (EstateID) **directly from the Vitec/Webtop UI**; Marketer receives a webhook (`installationId, estateId, orderId`), validates the property data, confirms the order back to the CRM, and hands the broker a **link to the Live report**. The orderable products set up in Vitec correspond to the company's M360 packages; the only new M360 UI is an "Order source" column `[M360, Vitec, Webtop]` (Vitec PRD).

**How it is realized — two services, distinct roles (verified against code):**
- **M2 owns the order webhook and the order lifecycle.** The webhook lands on M2 `Api::V1::Webhooks::CampaignOrdersController#vitec` / `#webtop` *(code — [`app/controllers/api/v1/webhooks/campaign_orders_controller.rb:9-35`](https://github.com/marketertechnologies/marketer/blob/ef140820a351afdf1818bc615aea7451bace1c9b/app/controllers/api/v1/webhooks/campaign_orders_controller.rb#L9-L35))*, which runs `CampaignOrders::Process::{Vitec,Webtop}`: validate → create the **Campaign Package Instance** → **M2 itself reports order status back to the CRM** via its own `Api::Vitec/Webtop::Client::UpdateOrderStatus` (`DELIVERED` once the instance is activated, else `INTERACTION_REQUIRED` with a redirect to Order Management) *(code — [`app/services/campaign_orders/process/vitec.rb:51-68`](https://github.com/marketertechnologies/marketer/blob/ef140820a351afdf1818bc615aea7451bace1c9b/app/services/campaign_orders/process/vitec.rb#L51-L68))*. On success the broker is redirected to **Order Management** (`M360_URL_BASE/orders?uuid=&token=` — `app/services/campaign_orders/url.rb:8-31`); for Webtop, when the order token has expired, to the **Live/Property Report** (`existing_home.live_report_url` — `app/services/campaign_orders/process/webtop.rb:140-141`). This M2 leg matches PRD steps 2–5.
- **CRM Gateway's role in THIS flow is the estate-data dependency — not the confirmation.** Before validating, M2's `CampaignOrders::Process::Base#fetch_estate` calls the gateway's **RPC `FetchEstate`** (`CrmGateway::EstateSyncJob`), auto-importing a blank product (`CrmGateway::AutoImport::CreateResources`) if none exists, so the estate is present and fresh for the order *(code — `app/services/campaign_orders/process/base.rb:15,106-111`)*. If estate/broker data is still syncing, M2 returns the retry error the PRD describes (step 3). So the gateway **supplies the data**; **M2**, not the gateway, sends the campaign-order status confirmation to the CRM.
- **Separately, the gateway has its own Vitec order-status/permission endpoint.** `GET /v1/orders/vitec/permissions/confirm` (basic-auth) enqueues `Vitec::UpdateOrderStatusJob`, which POSTs status `delivered` to Vitec's hub Orders API with the message *"Tilgang for M360 er bekreftet for oppdraget"* ("M360 access is confirmed for the assignment") — gateway `app/controllers/v1/orders/vitec/permissions_controller.rb:22-33` + `app/jobs/vitec/update_order_status_job.rb:9-31`. This is an **M360-access/permission** confirmation to Vitec, *distinct* from the campaign-package order status M2 manages above. *(Code-derived: no Jira/Notion intent doc for this endpoint was found — descriptions are blank tenant-wide and the gateway git history carries no ticket ref for it; flagged as code-only.)*

Data-change **notifications** (estate changed in the CRM → re-sync) arrive on the gateway's own `POST /v1/webhooks/vitec|webtop` *(code — gateway `app/controllers/v1/webhooks_controller.rb:10-17`)* — do not confuse these with M2's campaign-order webhook above.

<callout icon="⚠️" color="yellow_bg">
	**Flag 2 — packaging intent vs code wiring (not a bug):** *Intent* (operator, 2026-07-23; corroborated by the Vitec PRD's closing "Link to Live report" step): for a CRM-integrated 3rd party, **Order Management + the Property/Live Report are experienced together as one broker-experience package**. *Code:* there is **no single bundling object** — Order Management (the standalone token-auth Orders SPA on M360) and the Live/Property Report (a separate report app driven by `LIVE_REPORT_URL`) are **independent surfaces**, stitched together by the **M2 order flow** (which redirects to Order Management and, on token expiry, surfaces `live_report_url`). CRM Gateway wires neither surface — it feeds the estate/broker data and (separately) the access grant. The divergence is packaging/altitude, **not incorrect behaviour** — flagged, not reconciled.
</callout>

## Vitec checklist-based auto-ordering (`MarkChecklistJob`)
*Partial backfill 2026-07-23 — pending operator gate.*

Beyond the broker-initiated "order from inside the CRM" flow above, M2 can **write back to a Vitec checklist** so the customer's own Vitec macro places a campaign order. `Vitec::Orders::MarkChecklistJob` PUTs a checklist tag to Vitec when an `ExistingHome` (a second-hand-Vitec property) first reaches a phase, keyed by a per-phase config:
- **`ORDER_CAMPAIGN`** (pre-existing) — fires on the first transition to **`for_sale`** (new `listed_at` timestamp); tag value from company setting `settings.vitec.order_campaign_tag`.
- **`ORDER_CAMPAIGN_KFS`** (added by [HK-263](https://linear.app/newbuilds/issue/HK-263)) — fires on the first transition to **`coming_for_sale`** / signing (new `signed_at` column); tag value from the new company setting `settings.vitec.order_campaign_kfs_tag`. "KFS" = *Kommer for salg* ("coming for sale").

Both triggers are **scoped to second-hand Vitec properties** (`estate_type` nil both before and after the sync **and** `synced_from_vitec?`) and are **idempotent per phase** (the `listed_at` / `signed_at` timestamps are set once, and the job is `unique :until_executed`). Source: [HK-263](https://linear.app/newbuilds/issue/HK-263) (hotfix), PR [#14108](https://github.com/marketertechnologies/marketer/pull/14108) (M2 `app/jobs/vitec/orders/mark_checklist_job.rb`, `app/services/crm_gateway/receive/existing_home.rb`, `app/models/existing_home.rb`).

> **Intent note (ticket-sourced):** the product rationale — ticking the checklist point makes the customer's Vitec macro order the KFS campaign, a workaround for Vitec Next's broken checklist auto-run — is stated on [HK-263](https://linear.app/newbuilds/issue/HK-263), **not** in the PR body (which describes only the mechanism). Which concrete product the KFS macro ultimately orders is an open EM1 detail.

> **Observability of this round-trip (BE v1.376.0 release sync 2026-08-26 — pending operator gate):** the outbound leg described here (`MarkChecklistJob` → checklist tag → Vitec places the order → the order webhook lands back on M2) and the inbound leg described above now have a dedicated admin-panel surface, documented on the sibling deep-dive [Order-Intake Observability](order-intake-observability.md). Three audit tables landed for it — `campaign_order_intake_receipts` (one row per Vitec / Webtop / M360-portal intake attempt, with a rejection stage), `vitec_auto_order_attempts` (one row per pipeline stage per Sidekiq attempt, stages `crm_gateway_received` → `checklist_pushed` → `orders_fetched` → `order_status_fetched` → `order_processed`) and `vitec_checklist_pushes` (one row per PUT this job makes, carrying the `ORDER_CAMPAIGN` / `ORDER_CAMPAIGN_KFS` tag) — plus two panels reading them ([HK-473](https://linear.app/newbuilds/issue/HK-473) · PR [#14188](https://github.com/marketertechnologies/marketer/pull/14188); [HK-476](https://linear.app/newbuilds/issue/HK-476) → [HK-508](https://linear.app/newbuilds/issue/HK-508)). ⚠️ **The writers do not exist yet:** [HK-474](https://linear.app/newbuilds/issue/HK-474) (intake writes) and [HK-475](https://linear.app/newbuilds/issue/HK-475) (`MarkChecklistJob` + stage writes) are both still *In Review* at tag `v1.376.0`, so `MarkChecklistJob` records nothing today and the panels are empty in production.

## Employee images — which Broker records an image attaches to
*Release sync 2026-09-01 (BE v1.377.0) — pending operator gate.*

**The defect.** When the gateway delivers an **employee image**, M2's `CrmGateway::Receivers::EmployeeImage` has to decide which `Broker` and `Agent` records the image belongs to. For brokers it resolved them by walking the **estate the payload happened to reference** — the `ExistingHome`s behind the payload's products, then the `Broker::Assignment` rows on those homes. Since the CRM side froze a single estate at file-fetch time, *"an employee managing N estates only had the image attached to one Broker product"*, so a broker's profile photo appeared on one of their properties' broker surfaces and not the rest.

**The fix (M2 side, v1.377.0).** `find_brokers` no longer takes the products — it takes the payload's **CRM configuration** and the employee's **external id**, and resolves brokers globally within that configuration: `Product.for_crm_configuration(crm_configuration).of_type('Broker').where(external_id:)`, then `Broker.where(id: <those products' promotable_ids>)`. It short-circuits to `Broker.none` when either the CRM configuration or the external id is blank. The **agent** lookup (`find_agents`, still project-scoped) and the auto-import retry path are **unchanged** — the second commit on the PR deliberately narrowed an initially broader fan-out back to brokers only. Product effect: one CRM sync now attaches the photo to every applicable Broker record for that employee, instead of one arbitrary estate's. [HK-538](https://linear.app/homekeytechnologies/issue/HK-538) · PR [#14226](https://github.com/marketertechnologies/marketer/pull/14226) (merge `3a15d99b`); code read at tag `v1.377.0` (`app/services/crm_gateway/receivers/employee_image.rb:29,47-55`). Related: Glossary *Broker*, *Product*, *CRM Configuration*.

> ⚠️ **Source caveat — an access gap, not an inference.** [HK-538](https://linear.app/homekeytechnologies/issue/HK-538) lives in the **`homekeytechnologies`** Linear organisation. Linear has split into two organisations and this KB's API key reads only `newbuilds`, so querying HK-538 returns `Entity not found: Issue`. ## `assignment_category` (CRM → M360)
*Partial backfill 2026-07-23 — pending operator gate.*

When the gateway's estate data is received, M2 derives an `assignment_category` on the `ExistingHome` from the CRM's assignment / case classification. [HK-284](https://linear.app/newbuilds/issue/HK-284) taught the **Webtop** adapter to distinguish commercial **sale** vs **rent**: its `assignment_category` now returns the base category unchanged **unless** the base `CaseCategoryType` maps to `industry`, in which case it consults `COMMERCIAL_ASSIGNMENT_TYPE_MAPPER[assignment_type]` and yields **`commercial_sale`** or **`commercial_rent`** (falling back to bare `industry` for unmapped types). Previously all commercial Webtop cases collapsed to a blanket `industry`. This brings Webtop's sale/rent distinction to parity with the **Vitec** adapter's pre-existing `ASSIGNMENT_TYPE_GROUP_MAPPER`, which emits `commercial_sale` / `commercial_rent` / `commercial_area`. *(The Webtop mapper emits only **`commercial_sale`** / **`commercial_rent`**; **`commercial_area`** originates from the Vitec side.)* Source: [HK-284](https://linear.app/newbuilds/issue/HK-284), PR [#14129](https://github.com/marketertechnologies/marketer/pull/14129) — co-shared with [HK-297](https://linear.app/newbuilds/issue/HK-297), which adds the `commercial` **estate_type** value that consumes these `commercial_*` categories (see Glossary *Estate Type*). M2 `app/services/crm_gateway/adapters/webtop/dictionary.rb`, `.../webtop/existing_home.rb`; Vitec side `.../vitec/dictionary.rb`.

> ⚠️ **Open integration gap (flagged, not a bug):** the Webtop `COMMERCIAL_ASSIGNMENT_TYPE_MAPPER` covers 7 of 21 Webtop `AssignmentType` values. Two — **`ResaleOfContractPositionProff`** and **`ResaleOfContractPositionConsumer`** — could plausibly appear under `CaseCategoryType='Industry'` but are **unmapped**, so they fall through to bare `industry`. PR #14129 explicitly notes this needs confirmation from the Webtop integration; it is an open question, not intended behaviour.

## FINN URL in `payload[:link]` — gated to commercial estates
*Release sync 2026-08-11 (v1.373.0) — pending operator gate.*

**Contract (intent):** a **FINN** URL is only ever a valid destination for a **commercial** property. A regular (non-commercial) ExistingHome must resolve its destination through the CRM configuration's `existing_home_link_template` — the broker's own domain (e.g. `eiendomsmegler1.no/boliger/mn-…`), which itself redirects according to listing status. Stated on [HK-434](https://linear.app/newbuilds/issue/HK-434) as a contract clarification from Tekla in-thread: *"we should never use the FINN url for regular EH properties."*

**What went wrong.** Two crm-gateway changes that shipped 2026-07-23 as part of the commercial-properties work began emitting `link: <FINN URL>` on **generic-client** estate representers *without* gating on assignment category — Vitec ([HK-279](https://linear.app/newbuilds/issue/HK-279), crm-gateway PR #1028) and Webtop ([HK-280](https://linear.app/newbuilds/issue/HK-280), crm-gateway PR #1027) — so every *regular* EH on the generic path carried one too. M2's `CrmGateway::Adapters::Base#link` preferred `payload[:link]` over the template, writing the FINN URL into both `Product#link` and `ExistingHome#destination_url`, and `CampaignPackages::Instance#existing_home_url` then served it to the CFS landing page. On unpublished listings the propagated URL was a FINN **preview** URL (`preview.html?finnkode=…&secret=…`), publicly exposing a property *before* it was officially for sale — a seller-privacy issue. Blast radius reported on the ticket: **995** rows on FINN URLs, of which **80** were preview URLs (the privacy-critical set) and 915 merely wrong (should have been the broker's landing page). [HK-434](https://linear.app/newbuilds/issue/HK-434).

**The fix (M2 side, v1.373.0).** `Base#link` no longer short-circuits on `payload[:link]` directly — it asks a new `use_payload_link?(payload)` hook whose Base default preserves the old behaviour (`payload[:link].present?`), so the broker / project / stages adapters are unchanged. The three adapters that consume FINN links override the hook to additionally require a **commercial** estate:
- **Vitec `ExistingHome`** — `payload[:raw_assignment_type] ∈ {6, 8, 9}` (`commercial_area` / `commercial_sale` / `commercial_rent` in `Dictionary::ASSIGNMENT_TYPE_GROUP_MAPPER`).
- **Webtop `ExistingHome`** and **`ParentExistingHome`** — `Dictionary::CASE_CATEGORY_TYPE_MAPPING[payload[:case_category_type]] == 'industry'`.

A non-commercial estate therefore falls back to `existing_home_link_template`; where no template is configured, `destination_url` / `product.link` are left **blank** rather than FINN. Commercial estates keep the FINN URL exactly as before. [HK-434](https://linear.app/newbuilds/issue/HK-434) · PR [#14174](https://github.com/marketertechnologies/marketer/pull/14174) (merge `3a9d7cd6`; a hotfix branched off `master`, not `development`).

> **Still open — stated out of scope on the ticket, not a gap in the fix:** (a) **data mitigation** for already-persisted rows (paused campaigns, backfilling correct landing pages, republication) is handled manually from the Rails console, so rows synced *before* the fix keep their FINN URL until that estate next syncs; (b) the **crm-gateway-side root fix** ("Option B" — stop emitting `finnLink` for non-commercial estates in the Vitec/Webtop representers) is an optional follow-up and did **not** ship here, so the gateway still emits the field and M2 is the only thing filtering it. Both per [HK-434](https://linear.app/newbuilds/issue/HK-434). Related: Glossary *Existing Home* (`destination_url`), and the [Flow deep-dive: Broker Experience — CRM Order → Live Ads → Completion on Sale](../user-flows-and-journeys/flow-broker-experience-crm-order.md) for how `existing_home_url` feeds the CFS landing page.
