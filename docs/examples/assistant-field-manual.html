01 · substrate

What I run on

This project has no application code of its own. It's a spore-managed coordinator: a long-lived process that reads a small set of markdown skills, watches an inbox, and mints short-lived workers to do the actual reading and writing.

Two separate channels reach the coordinator, and only one of them carries content. A message inbox holds full tell envelopes — a new thread, a reply, a worker reporting done. A poke channel carries nothing but a wake-up signal; a poke means "go check the message inbox," never the payload itself.

State doesn't live in conversation memory. state.md is the only thing guaranteed to survive a restart — and restarts happen often, on a token budget, mid-investigation. Every pipeline below is written so a coordinator with zero memory of this conversation can pick it back up from disk.

03 · investigation

Investigating a bug

A bug report gets a checked answer, not a plausible-sounding guess. One investigator drafts a finding; two independent verifiers attack it in parallel, checking two different things neither one can substitute for.

Everything the investigator finds needs a checkable pointer — file:line, a Sentry link, a Linear ID, an exact log line. No pointer, no claim. Repo access is always coordinator-mediated: a worker never clones on its own authority, so both verifiers check the exact same pinned commit the investigator saw.

check

Is the thread still quiet since the conclusion was reached?

Fast-moving incidents go stale in minutes — this is re-checked at the moment of posting, not against a snapshot from earlier.

new info

Kill both verifiers, discard their results, and restart Stage 1 with the new information folded in.

quiet

Continue.

action

Dispatch a full independent verifier

One more pass, right before anything is said in public: re-check the entire conclusion, every citation, fresh — not just the specific flags raised earlier.

check

Cleared to post?

Gated by whether the owning engineers are already visibly diagnosing live in-thread, and by any standing operator hold on that channel.

held

No Slack post. The KB entry and any Linear filing proceed anyway — they don't depend on whether anything gets said in the thread.

clear

The coordinator composes one reply — 3–5 short sentences, the verified conclusion plus at most one open ask. Caveats and dropped candidates stay out of it.

check

Does the verdict name an application bug?

yes

File a Linear ticket (duplicate search first) and notify the marketer-frontend coordinator to independently reproduce and confirm it — this project only ever reads other repos, it can't reproduce inside them.

no

Skip both, move straight to the record.

action

Write the KB entry

docs/investigations/<date>-<slug>.md — every outcome, always, including "checked X, Y, Z, found nothing relevant." Every citation and every logical step, kept individually, not summarized into a count.

04 · guardrails

Rules that override the default

Six standing rules, each written after watching the process get something wrong once. They bind every stage above, not just the ones that read them.

bot-mention-scope

Only a literal @harnessdebugger tag counts as addressed to this bot. "The harness" said in passing, by role or nickname, is out of scope by definition.

silence-during-live-debugging

Once the owning engineers are visibly diagnosing live in-thread, default to silence — unless asked directly, or holding a genuinely new, independently-verified fact.

verify-the-literal-symptom

An exculpatory verdict needs a citation against the report's own literal claim — not a status flag or completion timestamp that merely precedes it.

deploy-status

"Merged to the default branch" is not "deployed to production" on these repos — check the branch each repo's production actually tracks, per repo.

live-incident-verification-gate

Stay fast — single investigator, no second stage — while a team is actively debugging live. Never skip the full independent re-check gated right before a post.

short-slack-replies

Post like a dev answering in-thread: 3–5 sentences, one conclusion, at most one open ask. The full uncertainty picture lives in the KB entry, not the channel.

05 · case file

HK-618 — an order that wouldn't sync

Thread "Error when ordering — EM1" Reporter Anette Johansen Date 2026-09-22
STAGE 1

The investigator traced it to CrmConfiguration.for_companies — missing a .distinct — which makes crm_configurations.one? always false for the EM1 Midt-Norge Webtop company family (27–28 companies sharing one config row). The self-heal product-creation fetch never fires as a result. The specific estate in the report, 16260182, was confirmed absent from both the products and existing_homes tables — zero rows, either side.

2A · CONFIRMED

The citation re-opened clean against the same pinned commit.

2B · GAP FOUND

The bug is proven company-family-wide, but nothing tied it to confirming this reporter's order actually routed through one of the affected companies. The same DB-absence check had also been asked to stand in for a second, separate claim — that the error string itself persists — without ever tracing the code path that renders it.

GATEdowngraded

"possible solution" → leads-plus-stuck. The mechanism holds; the link to this specific order doesn't, yet.

HOLD

Not posted — a standing operator instruction to stay off that channel was already in force.

LIVE THREAD~6 hours

The owning engineers diagnosed it live, in-thread, through three different theories in sequence — a CRM-side marketability flag, a scheduler timing-window miss, a guard clause — before one of them traced it back to the exact same missing-.distinct query, unprompted:

"after another round seems the root cause why product wasn't created is the issue described in the ticket 😄 … creating a fix now"

No @-tag, ever. The default-to-silence rule held the whole way through — this bot never needed to speak, because the team got there on its own.

LINEAR

HK-618 filed directly once the verdict named a confirmed mechanism — duplicate search run first, two related-but-distinct tickets noted, not blocked on.

NOTIFY

The marketer-frontend coordinator was asked to independently reproduce it — this project can only read that repo, never confirm inside it.

KB

docs/investigations/2026-09-22-order-error-em1-sync.md — every citation, every 2b attack point, the exact reply that would have posted if the hold had lifted.

OUTCOME

The owning engineer opened a fix PR the same day. The finding was right; the silence rule meant it didn't need to be said to matter.
